# Обновление OpenAlbert на Pi

Запрос обновить установленный OpenAlbert разрешает загрузку образов и необходимый
перезапуск выбранных сервисов. Используй разрешения и ограничения текущей сессии.
Создание или редактирование этого скилла само по себе не запускает обновление.

## Контекст

- Хост по умолчанию — `mishankov@pi`, проект Compose — `openalbert`.
  Установка находится в `/home/mishankov/homelab/openalbert`; проверь фактический
  путь по labels контейнеров, прежде чем обращаться к данным.
- Читай [README установки](../../../openalbert/README.md),
  [Compose](../../../openalbert/compose.yaml) и [pi.env](../../../openalbert/pi.env).
  В этой установке `.env` загружается перед `pi.env`.
- В итоговой конфигурации используется `OPENALBERT_IMAGE_TAG=master`.
  Компоненты публикуются независимо: разные OCI revision labels нормальны.
  После выборочного выпуска общий SHA-тег может отсутствовать у неизменённых
  компонентов. Проверяй каждый нужный образ и платформу отдельно.
- `computer` — локальная сборка Ubuntu с `pull_policy: never`. Сохраняй её сервис,
  сеть, mounts, SSH-ключи и работающий контейнер при обычном обновлении приложения.
  `up.sh` собирает компьютер и запускает весь стек; для выборочного обновления
  используй явный список сервисов. `install.sh` и пересоздание компьютера нужны
  при изменении самого компьютера, а не при каждом обновлении backend.
- `container_data/computer` исключён из резервных копий; в приватном
  `backup-config/config.json` должно сохраняться `exclude_computer: true`.
  Обновление приложения не должно менять эту политику.
- Секреты и пользовательские данные остаются вне Git и вывода инструментов.
  Не печатай полный `docker inspect`, разрешённый `compose config` или `.env`.

## Подготовка обновления

1. Проверь рабочие деревья и найди действующий проект через SSH с `BatchMode=yes`:
   `docker compose ls --format json`, labels `com.docker.compose.project.working_dir`
   и `com.docker.compose.project.config_files`. Определи env-файлы, overrides,
   профили, пути данных и init-сервисы. Запиши фактические image IDs/digests,
   revisions и состояния контейнеров, в том числе ID и `StartedAt` компьютера.
   Локальный тег `master` уже мог измениться после предыдущего pull — сверяй
   именно работающий контейнер. Проверь место на диске и доступность `sudo -n`.
2. Сверь изменения с исходниками OpenAlbert и его инструкциями развёртывания.
   Если нужно обновить Compose, перенеси необходимые изменения в отслеживаемый
   файл. Upstream Compose не содержит нашего локального компьютера: сохраняй его,
   project name, сеть и mounts. Сохраняй LAN binding инспектора
   `192.168.1.31:8080`, loopback служебных портов и PostgreSQL `15432`.
   `INSPECTOR_PUBLIC_URL` не задаёт port binding.
3. Сохрани credentials, модели LLM/STT, группы Telegram, профили и лимиты.
   Не заменяй приватный `.env` шаблоном и не затирай локальные отличия при pull
   репозитория. Сначала сохрани их и установи назначение. Обновление checkout
   и его подмодуля само по себе не обновляет работающие контейнеры.
4. Подготовь конфигурацию в закрытом staging (`0700`, env-файлы `0600`).
   Используй `--project-directory` с действующим каталогом установки и явные
   `--env-file` и `-f`: иначе относительные mounts могут указывать на staging.
   Сравни разрешённые конфигурации в памяти, выводя только имена изменённых полей.
   Проверяй окружение, пути данных, сети и порты; ожидаемы лишь изменения плана.
   Один явный `-f` не подключает остальные overrides автоматически.
5. Для нужных опубликованных компонентов проверь `master`, ARM64-манифесты
   и OCI revisions, например через `docker buildx imagetools inspect`.
   HEAD исходников может ещё не быть опубликован. Определи изменившиеся сервисы;
   пересборка и публикация исходников — отдельная задача, при необходимости
   используй скилл `publish-changed-images` в checkout OpenAlbert.
   Недоступный нужный образ или платформа блокирует запуск кандидата.
6. Сохрани ссылки на прежние образы для отката до изменения тегов и загрузи
   выбранные образы, пока прежние контейнеры работают. Для защиты от смены
   `master` между проверкой и загрузкой можно скачать проверенный digest/SHA-тег
   конкретного компонента и присвоить ему локальный alias `master`.
   Сверь загруженные платформы и revisions с планом. Если доступ к registry есть
   только на Mac, Docker CLI с `--host ssh://mishankov@pi` позволяет использовать
   существующие credentials клиента для загрузки в Docker Pi.
   Не переноси приватный Docker config на сервер.

## Резервная копия и переключение

Сохрани исходные Compose/overrides, env-файлы, настройки backup и ссылки на старые
образы в отдельном каталоге с отметкой времени (`0700`, файлы с секретами `0600`).
Проверь последний успешный бэкап и выбери копию под конкретное изменение:

- Для обычного обновления приложения без миграций подходят свежий логический
  дамп его БД, проверенный через `pg_restore --list`, и копия knowledge вместе
  с конфигурацией и прежними образами. Учти другие изменяемые данные, если есть.
- При изменении версий хранилищ, миграциях или формата данных сделай согласованную
  копию затрагиваемых PostgreSQL/Temporal, MinIO и knowledge. Для файловой копии
  БД останови писателей и соответствующие сервисы; живая копия каталога БД
  не заменяет согласованный бэкап. Сохрани владельцев и права, проверь архив.
- Не включай `container_data/computer`, веса STT и логи в копию по инерции.
  Данные компьютера резервируются только при отдельном изменении этой политики.
  Не запускай deploy параллельно активному холодному бэкапу. Перед заменой
  контроллера проверь phase и очередь запросов в `container_data/backup-state`.

После проверки копии установи подготовленную конфигурацию на прежние пути данных.
Повтори `docker compose ... config -q`. Для обновления только приложения и
контроллера используй тот же набор env/Compose-файлов и команду вида:

```sh
docker compose ... up -d --no-deps --no-build --pull never --wait --wait-timeout 120 openalbert backup
```

Список сервисов определяется планом: обновляй только нужные компоненты. Если
меняются зависимости, учти их порядок запуска и готовность. `--pull never`
использует уже проверенные образы и не подтягивает другой выпуск посреди запуска.

Если копия не удалась до переключения, запусти прежние остановленные контейнеры
через `start`, а не `up`: тег `master` уже мог измениться. После неудачного нового
`up` сохрани диагностику; не повторяй тот же deploy без исправления причины.
Перед откатом образов проверь совместимость текущих данных. Не перезаписывай
живую БД из копии автоматически после возможной миграции.

## Проверка результата

- Проверь выбранные сервисы: работающие image IDs и revisions совпадают с планом,
  healthchecks проходят, неожиданных рестартов и ошибок запуска нет.
  Разные revisions у независимых компонентов допустимы. Init-сервисы текущего
  Compose, например `minio-init`, должны завершиться с кодом `0`; `computer-init`
  в нашей конфигурации отсутствует.
- Проверь `/healthz` и `/inspect/` по действующему binding. Проверь готовность
  затронутых Temporal/STT/S3 и сохранность данных по выбранным контрольным
  признакам, не выводя содержимое сообщений или документов.
- При обычном обновлении ID и `StartedAt` компьютера сохраняются. Если для
  согласованной копии потребовалась его запланированная остановка, после старта
  проверь тот же контейнер и данные. Проверь SSH, Python и беспарольный sudo
  пользователя `albert`.
- После обновления backup проверь чтение статуса и списка S3-копий, сохранение
  `exclude_computer: true`, расписания и retention. Сам запуск контейнера
  не подтверждает успешный бэкап; завершение новой копии подтверждается отдельно.
- Проверь diff: credentials, данные, архивы и staging не должны попасть в Git.
  Commit/push, публикацию образов и изменения других установок выполняй в рамках
  запроса и уже выданных разрешений сессии.
- Сообщи хост, обновлённые компоненты, их фактические revisions, результаты
  проверок и путь к копии для отката. Если проверка не завершена, укажи это явно.
