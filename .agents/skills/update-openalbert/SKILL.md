# Обновление OpenAlbert на Pi

Запрос обновить установленный OpenAlbert разрешает загрузку образов и необходимый
перезапуск выбранных сервисов. Используй разрешения и ограничения текущей сессии.
Создание или редактирование этого скилла само по себе не запускает обновление.

## Контекст

- Хост по умолчанию — `mishankov@pi`, проект Compose — `openalbert`.
  Установка находится в `/home/mishankov/homelab/openalbert`; проверь фактический
  путь по labels контейнеров, прежде чем обращаться к данным.
- Читай [README установки](../../../openalbert/README.md),
  [Compose](../../../openalbert/compose.yaml) и [pi.env](../../../openalbert/pi.env).
  В этой установке `.env` загружается перед `pi.env`.
- В итоговой конфигурации используется `OPENALBERT_IMAGE_TAG=master`.
  Компоненты публикуются независимо: разные OCI revision labels нормальны.
  После выборочного выпуска общий SHA-тег может отсутствовать у неизменённых
  компонентов. Проверяй каждый нужный образ и платформу отдельно.
- `computer` — локальная сборка Ubuntu с `pull_policy: never`. Сохраняй её сервис,
  сеть, mounts, SSH-ключи и работающий контейнер при обычном обновлении приложения.
  `up.sh` собирает компьютер и запускает весь стек; для выборочного обновления
  используй явный список сервисов. `install.sh` и пересоздание компьютера нужны
  при изменении самого компьютера, а не при каждом обновлении backend.
- `container_data/computer` исключён из резервных копий; в приватном
  `backup-config/config.json` должно сохраняться `exclude_computer: true`.
  Обновление приложения не должно менять эту политику.
- Секреты и пользовательские данные остаются вне Git и вывода инструментов.
  Не печатай полный `docker inspect`, разрешённый `compose config` или `.env`.

## Основной путь: скрипт обновления

Для обычного обновления используй [update.py](../../../openalbert/update.py).
Он реализует выбор образов, блокировки, копию, переключение и проверки; не
воссоздавай эти шаги одноразовыми SSH-скриптами. Команды выполняй из корня этого
checkout на рабочей станции с доступом к registry. Нужны Python 3.9+, Docker CLI
с Buildx, инициализированный `vendor/openalbert`, BatchMode SSH и `sudo -n` на Pi.
Приватный Docker config остаётся на рабочей станции.

1. Проверь рабочее дерево и сформируй новый план вне Git:

   ```sh
   update_plan_dir="$(mktemp -d "${TMPDIR:-/tmp}/openalbert-update.XXXXXX")"
   python3 openalbert/update.py plan --output "$update_plan_dir/plan.json"
   ```

   Планирование читает установку и registry, без загрузки образов, остановки
   сервисов и запросов к LLM. Скрипт сам определяет каталог, все Compose/env-файлы
   по labels и сравнивает конфигурацию с работающими контейнерами. Если нужен
   другой разрешённый хост или checkout исходников, передай `--host` и `--source`
   перед подкомандой; используй тот же хост при применении и восстановлении.

2. Прочитай `changed`, `blockers`, `baseline.warnings` и revisions/digests в
   `targets`. Код `0` означает готовый план, `2` — план с блокерами, `1` — ошибку.
   Если `changed` пуст и блокеров нет, сообщи, что обновлений нет, и заверши.
   Если пользователь запросил только план, заверши после его разбора.
   Предупреждения, например о неприменяемом лимите памяти, отрази в результате.

3. При разрешённом обновлении и отсутствии блокеров примени именно этот план
   без дополнительного подтверждения:

   ```sh
   python3 openalbert/update.py deploy --plan "$update_plan_dir/plan.json"
   ```

   Если блокеры касаются только шаблонов Compose/env, проверь diff между ревизиями
   по ручному сценарию. Если текущая конфигурация совместима и штатная копия
   достаточна, передай в `deploy` отпечаток из вывода `plan` через
   `--reviewed-plan` и обоснование без секретов через `--review-reason`.

   План действует два часа; изменение конфигурации или контейнеров требует
   нового плана. Скрипт обновляет только изменившиеся `openalbert`, `backup`,
   `stt`, `log-gateway`, загружает проверенные ARM64 digest и сохраняет прежние
   образы до переключения. Для согласованной копии он приостанавливает приложение
   и контроллер backup; компьютер, PostgreSQL, Temporal и MinIO остаются работать.
   `deploy` делает два небольших тестовых запроса к LLM, до и после обновления.

4. Сохрани путь к каталогу запуска, который напечатал скрипт. По умолчанию это
   `/home/mishankov/openalbert-update-backups/<timestamp>-<id>/` на Pi.
   Успех подтверждают код `0`, `status.json` с `phase: completed` и итоговый
   `verification.json`. В отчёте проверь фактические образы/revisions и результаты
   HTTP, LLM, зависимостей, данных, компьютера и backup. Одного `/healthz`
   недостаточно для подтверждения доступа к модели. `backup-verified.json`
   подтверждает локальную копию; он не означает создание нового S3-бэкапа.
   Конфигурацию и журналы с приватными данными читай только на Pi, без вывода
   секретов. Не повторяй прошедшие проверки вручную без выявленной причины.

Подробные требования и форматы отчётов — в [README](../../../openalbert/README.md#updates).
Скрипт требует свежий подтверждённый S3-бэкап, свободное место, отсутствие активного
или ожидающего холодного бэкапа и запас до следующего запуска по расписанию.

## Остановки и восстановление

- При ошибке планирования или подготовки установи причину, устрани её в рамках запроса и создай
  новый план. Не меняй сохранённый план и не ослабляй проверки для обхода отказа.
  Отсутствие опубликованного образа или ARM64 блокирует обновление; сборка и
  публикация образов остаются отдельной задачей.
- Изменения MinIO, Compose/env-шаблонов, SQL/schema/storage и реализации backup
  скрипт направляет на ручной разбор. Его проверки консервативны и не доказывают
  совместимость произвольных изменений исходников. Для такого случая прочитай
  [ручной сценарий](references/manual-update.md), сверь исходники и подготовь
  подходящий план копии и переключения перед продолжением в разрешённых рамках.
- После сбоя или обрыва связи сначала прочитай `status.json` и дождись завершения
  очистки работающего worker. До попытки развёртывания скрипт запускает прежние
  остановленные контейнеры через `start`; успешное такое завершение имеет фазу
  `aborted_before_deployment` и `originals_restarted: true`.
- После жёсткого прерывания, если `deployment_started: false` и worker уже
  завершился, задай `update_run_dir` фактическим каталогом запуска из вывода
  скрипта и восстанови прежние контейнеры командой:

  ```sh
  python3 openalbert/update.py recover --run-dir "$update_run_dir"
  ```

  `recover` проверяет блокировки, конфигурацию и ID
  контейнеров; успешная фаза — `recovered_before_deployment`.
- Если новая версия уже запускалась (`deployment_started: true`, в том числе
  `failed_after_deployment`), изучи сохранённые журналы и ручной сценарий.
  Не повторяй deploy без устранения причины; перед откатом образов оцени
  совместимость данных. Живая БД автоматически из копии не восстанавливается.

## Итог

Сообщи хост, обновлённые компоненты и их фактические revisions, результаты проверок,
предупреждения и путь к копии для отката. Если обновлений нет, явно сообщи это.
Если запуск или проверка остановились, укажи причину, фазу и оставшуюся работу.
Проверь diff: секреты, данные, архивы и планы не должны попасть в Git.
Commit/push и действия с другими установками выполняй в рамках запроса и ранее
выданных разрешений сессии.
